# GPUI 版 AI からの編集（工数の一括修正・プロジェクト作成・取り消し）設計

日付: 2026-11-12 / ブランチ: `gpui-native`（未マージのまま続ける）

## 目的と理由

UI だと面倒な作業を、Codex / Claude Code に言葉で頼めるようにする。代表例は「このプロジェクトで登録してきた一連の作業のエントリーを、まとめて別プロジェクトに付け替える」。
いまの `track-cli` は工数の作成と読み取り（`status` / `projects` / `list` / `prepare` / `create`）しかできない。

利用者の言葉:
- 稼働データ（工数）は**なんでもいじれるように**したい
- **設定画面でできることも任せたい**（クライアント・プロジェクト・タグの作成・名前・色・アーカイブ、タグの削除）
- 工数を記録するとき、**明らかに登録済みプロジェクトに一致しないときは、作るかを利用者に確認**させたい
- 一番困るのは**想定していない書き換え**。だから **Undo できる仕組み**がほしい。取り消しは **AI との会話からも、Track の画面からも**できると嬉しい
- 確認は**件数が多いときだけ**でよい

## 方針

AI は今と同じく同梱の `track-cli` を呼ぶ。CLI は「指定した ID のものを、指定した値に変える」という確実な操作だけを持ち、どれを変えるかの判断（会話の解釈・検索）は AI 側が `list` などで行う。Codex と Claude Code の両方で同じように使えること（スキル／コマンドの文面は両方更新する）。

## 決まったこと

### AI ができること（CLI に足す）
- **工数**: 複数件まとめての変更（プロジェクト・タイトル・メモ・タグ・開始/終了時刻・休憩）と削除。既存の作成はそのまま
- **工数を探す**: 期間に加えてプロジェクト・語句で絞り込めるようにする（付け替え対象を AI が集めるため）
- **クライアント・プロジェクト・タグ**: 作成、名前変更、色、アーカイブ／解除、プロジェクトのクライアント変更、タグの削除。規則は設定画面と同じ `track-core` の関数を使う（クライアント・プロジェクトは削除せずアーカイブ。設定画面と同じ）
- 設定（勤務時間・出力フォーマット・AI・バックアップ）とバックアップ／復元は対象外

### 確認のルール（CLI 側でも強制する）
既存の `create --confirmed` と同じく、確認が要る操作は `--confirmed` が無ければ CLI がエラー（`confirmation_required`）で止め、AI に一覧を見せて許可を取るよう促す。
- **10 件以上**の工数をまとめて変えるとき（9 件以下は確認なしで実行してよい）— 件数の境目は Claude の判断
- **削除**は件数によらず確認 — Claude の判断（取り消せても気づきにくい）
- **プロジェクト・クライアントの新規作成**は必ず確認（利用者の希望）。記録時に明らかに一致するプロジェクトが無いときは、既存に寄せず「作りますか」と聞く。クライアントも既存から候補を出し、無ければ作るかを一緒に聞く
- 名前・色・アーカイブなど設定系の変更は 1 件ずつなので確認不要（Claude の判断）

### 取り消し（Undo）
- AI が CLI 経由で書き換えるたびに、**1 回のコマンド = 1 つの操作**として、変更前と変更後の状態を DB に記録する（工数・タグ付け・クライアント・プロジェクト・タグ）。作成は「消せば戻る」、削除は「元に戻せば戻る」
- **会話から**: `track-cli undo [<操作ID>]`（省略時は直近の未取り消しの操作）。AI は「さっきのを戻して」で呼ぶ。操作の一覧も出せる（`track-cli history`）
- **画面から**: GPUI アプリが AI の新しい操作を検知したら「AI が N 件変更しました［元に戻す］」を出す。押すと同じ取り消しを実行する
- 取り消すのは **AI の操作だけ**。画面で手で直した分は対象外
- 取り消し対象の行が、その操作のあとに**別の変更を受けていたら上書きせず止めて**、どれが変わっているかを返す（部分的には戻さない）— Claude の判断
- 取り消し自体はやり直し（Redo）を持たない — Claude の判断（必要になったら足す）

### 開発中の安全
- これまでどおり DB は `~/.track-gpui` のコピーだけを扱う
- AI 連携の文面は開発用の別名（`track-dev`）で入る。本物の `track` スキル／コマンドは触らない

## 実装の前提（Claude の判断）
- 操作の記録は DB の新しいテーブルに置く。`database/migrations` に手書き SQL を 1 本足す（GPUI 版も Tauri 版も同じ仕組みで適用する。Tauri 版は使わないテーブルを無視するだけ）
- 記録は直近 100 操作または 30 日を残し、古いものは消す
- 一括変更は 1 トランザクション。途中で失敗したら何も変えない
- アプリの外部変更検知（1 秒以内）はそのまま使い、そのとき新しい操作があれば表示を出す

### レビューで出た点への判断（すべて Claude の判断）
- **AI 記録（`AiRegistration`）との関係**: 既存の `create`（AI の記録）も 1 つの操作として記録する。それを取り消したら、その操作で作られた `AiRegistration` の行も消す。そうすれば同じ時間帯が `prepare` で再び提案され、同じ `request-id` の再記録も replay 扱いにならない。工数の削除や付け替えでは `AiRegistration` は触らない（既存の SET NULL のまま）
- **タグ削除の取り消し**: 外部キーで一緒に消える工数・プロジェクトへのタグ付け（`TagOnEntry`・`TagOnProject`）も削除前に保存し、取り消しで戻す
- **「あとで別の変更を受けた」の判定**: 列は足さない。記録した「変更後」と現在の行（タグ付けを含む）が完全に一致するかで判定する。画面での手修正も別の変更として扱う。1 行でも一致しなければ操作全体を止める。取り消した操作には取り消し済みの印を付け、`history` に残す。同じ操作は 2 回取り消せない
- **確認の数え方**: 「10 件以上」はそのコマンドで変わる工数の件数で数える。クライアント・プロジェクトの作成は、記録時でも利用者が明示的に「作って」と言ったときでも常に `--confirmed` を要求する（明示的な依頼はそれ自体が許可なので、AI はその場で付けてよい）。1 コマンド = 1 操作で、プロジェクト作成と付け替えは別のコマンド・別の操作にする
- **画面での表示**: アプリは起動時点の最新の操作を覚え、それより新しい操作だけを出す（起動前の操作は出さない）。表示中に別の操作が来たら、最新の操作の表示に置き換える。取り消しは DB のトランザクション内で取り消し済みの印を確かめるので、画面と CLI から同時に押しても二重には戻らない
- **記録の大きさ**: 件数が多い一括削除でも全件を保存する。古い記録の間引き（100 操作・30 日）で抑える
- **migration**: `database/migrations` に足す。本物の `~/.track` に適用されるのはマージして Tauri 版を更新したときだけ。バックアップの検証は必須テーブルの有無だけを見るので、知らないテーブルがあっても困らない。Prisma スキーマには載せない

## 対象外
- 設定（勤務時間・出力フォーマット・AI・バックアップ）の変更、バックアップ／復元
- 画面で手で行った変更の取り消し（Undo 全般）
- クライアント・プロジェクトの削除（設定画面と同じくアーカイブだけ）
- Redo

## やってはいけないこと
- 確認が要る操作を `--confirmed` 無しで実行できてしまうこと
- 取り消しで、そのあと別に直された内容を黙って上書きすること
- 本物の `~/.track` や本物の `track` スキル／コマンドを書き換えること

## 実装者に任せること
- CLI のサブコマンド名と引数の形（既存の `create` の流儀に合わせる）
- 操作記録テーブルの列の形（変更前後を JSON で持つ等）
- 画面の「元に戻す」表示の見た目と、出しておく時間
- スキル／コマンド文面の書き方（確認ルールと取り消しの案内を含めること）
