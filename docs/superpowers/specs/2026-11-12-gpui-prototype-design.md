# Track GPUI 試作 — 設計

日付: 2026-11-12 / ブランチ: `gpui-prototype`

## 目的と背景

GPUI（Zed が使う Rust 製 UI フレームワーク）を実際に触り、**Track のカレンダー画面とレポート画面を今の React 版と同じものとして作れるか**を確かめる。Tauri 版に不満があるわけではなく、GPUI を体験すること自体が主な動機。採用するかは出来上がりを見て決める。

成功の基準は「今の画面と並べて触ったとき、同じ機能・同じ操作で使えるか」、そして「作ってみて GPUI での開発がどうだったか」を判断できる材料が揃うこと。

## ゴール / 非ゴール / アンチゴール

**ゴール**
- カレンダー画面とレポート画面を、機能を減らさずに GPUI で再実装する（下の機能一覧が基準）
- 表示だけでなく、ドラッグでの作成・移動・伸縮、編集ダイアログ、キーボード操作の手触りまで確かめられる
- 共通ヘッダー（カレンダー／レポート切替、日付移動）とショートカット `⌘1` `⌘2` `⌘[` `⌘]` `⌘T` `⌘+` `⌘-`
- 作り終えたら「GPUI でどうだったか」の所感メモを残す（下の「完了時の成果物」）

**非ゴール**
- 設定画面、メモ画面、データの移行、アップデート確認、リリースノート、AI 連携インストーラ、About
- `.app` 化・署名・配布、Tauri 版の置き換え
- タッチ操作（長押し・振動）。デスクトップ専用のため
- KING OF TIME / Outlook のモック表示（今の React 版でも定数 `MOCK_INTEGRATIONS_VISIBLE=false` で無効）
- favicon の進捗表示（ネイティブアプリには対応物がない）
- データの保存処理やレポート集計を Rust で書き直すこと（本採用になった時の作業）

**アンチゴール（こうなったら失敗）**
- 既存の React / Tauri / Bun のコードに手を入れる。試作は `gpui/` 内で完結させる
- 「GPUI では難しかったので機能を落とした」を黙ってやる。難しかった箇所は落とさずに挑み、どうしても無理なら所感メモに理由と一緒に記録する（それ自体が検証結果）

## 決まっていること（ユーザーの判断）

- データは試作では**既存の Bun API に HTTP でつなぐ**（`npm run local`、既定 `http://127.0.0.1:8787`、`TRACK_PORT` で変更可）。本採用時は Rust で作り直す前提なので、API クライアントは使い捨てでよい
- 動作確認は**コピーした DB で行う**。本物の `~/.track/` には書き込まない
  - 準備: `~/.track-gpui/` を作り、`sqlite3 ~/.track/track.db ".backup ~/.track-gpui/track.db"` で DB を写す（WAL モードなので単純なファイルコピーは避ける）。`config.json` も写す（AI プロバイダ設定のため）
  - 起動: `TRACK_DATA_DIR=~/.track-gpui npm run local`。この手順は `gpui/README.md` と準備スクリプトに残す
  - AI 機能を試すと、コピーとはいえ実データの内容が AI プロバイダに送られる点は今の React 版と同じ
- レポートは**基本全部**（カスタム出力・AI 週報まで含む）
- 表示から作り始め、操作感の確認まで進める。まとめて作るほうが効率的ならまとめてよい

## 技術方針（Claude の判断）

- 置き場所: リポジトリ直下の `gpui/` に独立した Cargo プロジェクト（ルートの npm ビルドとは無関係）
- UI 部品: **`gpui-component`（Longbridge 製、0.9.x）を使う**。入力欄（日本語 IME 対応）、セレクト、ポップオーバー、ダイアログ、通知、表、日付ピッカー、ドーナツ／円グラフが揃っており、GPUI 本体だけでは入力欄すら自作になるため。gpui 本体はこのライブラリが固定している `gpui-pre`（Zed の週次スナップショット）に従う。バージョンは `=` で固定し、試作中は上げない
  - 情報源: crates.io `gpui` は 0.2.2（2025-10）で古いまま。最新 API は Zed の git か `gpui-pre`。`gpui-component` 0.9.1（2026-11-09）が `gpui-pre =0.3.12` を指定
- ビルド環境: この Mac は Xcode 本体がなく Command Line Tools のみ（`metal` コマンドなし）。`gpui_platform` の `runtime_shaders` 機能を有効にしてシェーダーのビルド時コンパイルを避ける。それでもビルドできなければ Xcode 本体のインストールが必要（ユーザー作業）
- HTTP: `reqwest` を専用の tokio ランタイム上で動かし、GPUI の非同期タスクから待つ（GPUI は独自の smol 系実行器を使うため、tokio を直接混ぜない）。SSE と AI の NDJSON ストリームも reqwest のストリームで読む
- 日付: `chrono` + 日本語の曜日表記は自前。週は日曜始まり（今の仕様どおり）。時刻はローカルタイムで扱い、API には ISO（UTC）で送る
- 祝日: 日本の祝日データを持つ Rust クレートを使う（なければ内閣府 CSV 相当の表を同梱）。どれを使うかは実装者に任せる
- 永続化: localStorage の代わりに `~/.track-gpui/gpui-prototype.json` に保存（ズーム段階、レポートの展開状態・まとめる・サマリー折りたたみ、カスタム出力キャッシュ）。URL クエリ同期は不要（アプリ内の状態として持つ）
- ネイティブメニュー: `cx.set_menus` で「表示」メニュー（カレンダー／レポート、前の期間／次の期間／今日、拡大／縮小）を作り、ショートカットはアクション経由で同じ処理に流す

### うまくいかない時の逃げ道（Claude の判断）
- 固定した `gpui-component` / `gpui-pre` でビルドできない、または必要な部品が壊れている場合は、別バージョンや Zed の git リビジョンへの切り替え、部品の自作（例: ドーナツグラフを `canvas` で描く）をしてよい。何を変えたかは NOTES.md に書く
- Xcode 本体のインストールが必要と分かった時だけ止まってユーザーに頼む

## 機能一覧（ここが「同じもの」の基準）

元の実装の場所を添える。範囲はこの一覧が基準。実装中に元コードで一覧にない挙動を見つけたら、それも再現する（Claude の判断。「同じものが作れるか」の検証なので）。詳細な挙動は元コードを正とする。

### 共通ヘッダー（`src/client/components/AppHeader.tsx`, `ui/DateRangeNavigator.tsx`, `ui/DatePickerPopover.tsx`）
- 高さ 44px、濃い緑。左にカレンダー／レポートのタブ（下線で選択表示）。メモタブと ⋯ メニューは非ゴール
- 日付ナビと画面ごとの操作は、**今のコードどおり各画面上部のツールバー**に置く（`WeekCalendar.tsx:811`、`ReportsPage.tsx:841` の `ToolbarDateNavigation`）。CLAUDE.md の `HeaderDateNavigation` の記述は今のコードと合っていない（Claude の判断）。日付状態は画面ごとに持ち、`⌘[` `⌘]` `⌘T` は表示中の画面に届ける
- 日付ナビ: ‹ / 期間ラベル（押すと日付ピッカー）/ › / 今日（今日を含むとき強調）。ラベル形式「M月d日」「M月d日 – d日」「M月d日 – M月d日」「M月」
- 日付ピッカー: 日・週・月の3モード。日曜赤・土曜青・今日アンバー

### カレンダー（`WeekCalendar.tsx` ほか `components/calendar/*`）
- 表示日数: 1日 / 3日 / 稼働日（日曜始まりの週を `workDays` で絞る）/ 1週間。ウインドウ幅で 639px 以下は1日、767px 以下は週系を3日に（今の挙動）
- 時間軸 0:00–24:00、15分スナップ、上下に32pxの斜線バッファ。左60pxの時刻欄（1時間ごと、`hourPx≥96` で30分も）。30分は破線、1時間は実線
- ズーム3段階（1時間 48 / 96 / 192px、初期は96）。−/+ ボタンと `⌘+` `⌘-`。段階は保存
- 初回表示で「定時開始と現在時刻の早いほう −1時間」にスクロール
- 日付ヘッダー: 日付の丸、曜日1文字、祝日バッジ、その日の合計（休憩を除く `Xh Ym`）、今日はアンバー背景
- 勤務時間の網掛け: 稼働日（曜日が `workDays` に含まれ、祝日でない）だけ `workStart–workEnd` を白、それ以外は薄いグレー
- 現在時刻の赤線（60秒ごと更新）。ホバー線と「HH:MM」表示（操作中は動かしている端に追従）
- 重なりの配置: 開始昇順・終了降順で並べ、重なりのかたまりごとに空いている最小レーンへ（`layout.ts`）。幅・余白は `EntryBlock.tsx` に合わせる。0:00 終わりは 24:00 まで描く
- ブロック: 左3pxのプロジェクト色、色の混ぜ方は `index.css:66-101` の color-mix を再現。1行目タイトル（なければプロジェクト名）＋「HH:mm–HH:mm」、2行目プロジェクト名と正味時間（休憩込み表記）、タグの点と名前。ホバー・選択状態、上下6pxの伸縮つまみ
- 操作
  - 空き部分をドラッグして作成（15分未満は取り消し）→ 破線の仮ブロック＋プロジェクト選択ポップオーバー
  - ブロックをドラッグして移動（日をまたいで可、長さ保持、0–24時に収める）。変化があれば保存
  - 上下のつまみで伸縮（最短15分、日は固定）
  - クリックで選択、空き部分クリックで解除。ダブルクリックで編集ダイアログ
  - 選択中: Delete/Backspace で即削除、Esc で解除、↑↓で15分移動、Shift+↑↓で終了を15分伸縮
- 保存は楽観的更新（先に画面を変え、失敗したら戻して「更新に失敗しました」）。成功で「保存しました」。削除は「削除しました」通知に「元に戻す」ボタン（同じ内容で作り直す）
- プロジェクト選択ポップオーバー（作成時、幅280）
  - 手順1: 検索（プロジェクト名・クライアント名）、クライアントごとにまとめた一覧、最後に「プロジェクトなし」
  - 手順2: 戻る、タイトル入力（最大100、`/api/entries/titles` の前方一致候補を最大8件、↑↓ Enter Esc、IME 変換中は無視）、タグ（プロジェクトに紐づくタグは固定でオン）、メモ（最大500）、「作成 (⌘↵)」
- 編集ダイアログ「予定を編集」: タイトル、開始／終了（時刻のみ、15分刻み）、休憩（分、15刻み）、プロジェクト（検索つき選択、アーカイブ除外）、タグ、メモ。削除／キャンセル／保存、`⌘↵` で保存、Esc・背景クリックで閉じる
- 変更の自動反映: `GET /api/events`（SSE）の `track.connected` / `entries.changed` で表示中のデータを取り直す

### レポート（`ReportsPage.tsx`, `components/reports/*`, `lib/reportAggregation.ts`, `lib/reportCopy.ts`, `lib/reportOutputCache.ts`）
- 期間: 週 / 月、前後移動、今日。グループ: クライアント / プロジェクト / タグ（初期はプロジェクト）
- 絞り込み3種（クライアント・プロジェクト・タグ）の複数選択ポップオーバー: 検索、クリア、チェック・色・補足（プロジェクトにはクライアント名）。ボタン表記「すべての◯◯」「名前」「◯◯: N件」、選択中は濃色。クライアントを変えたら合わなくなったプロジェクト選択を外す。「すべてクリア」
- 集計サマリー: 件数、ドーナツグラフ（中央に Total と合計、項目ごとのグラデーション、ツールチップ）、凡例（色・名前・時間・割合・横棒）。折りたたむと細い積み上げ棒。広い画面は左300pxの列、狭いと上に積む
- 明細: 見出しと合計行が固定で本文がスクロールする表（内容・日時・タグ・時間・割合）。グループ行をクリックで展開し、そのグループの明細を `GET /api/reports/entries` で読む。全展開／全折りたたみ、「まとめる」（同じタイトルを合算、×件数）。空表示「この期間にデータがありません」
- カスタム出力ダイアログ: 形式の選択（設定の `reportCopyFormats`、なければ注意書き）、AI 使用／なしのバッジ、作成／再作成、AI のときは `POST /api/ai/generate-stream` を読みながら経過時間と「考えていること」「進捗」を表示、結果の表、結果をコピー（TSV/CSV、見出し行、引用符の規則は `reportCopy.ts`）、保存済み結果の復元（最大8件・7日）
- AI 週報（週表示のときだけ）: テンプレート（`{{期間}}` `{{合計時間}}`）からプロンプトを作り、生成結果の「## 主な作業」を固定文に差し替え。ダイアログで編集でき、再生成・コピー
  - 今の版は Milkdown（見たまま編集できる Markdown エディタ）。GPUI 版では複数行テキスト入力で Markdown をそのまま編集する形でよい（Claude の判断。同等の見たまま編集は試作の範囲を大きく超えるため）。描画プレビューを並べるかは実装者に任せる
- プロンプト組み立て・AI 結果の解析・コピー文字列の生成は今の TypeScript をそのまま Rust に移す（ここはロジックの移植で、UI 検証の本題ではないが、同じ結果を出すのに必要）

### 使う API（すべて `http://127.0.0.1:8787/api/...`）
`GET /entries?from&to`、`GET /entries/titles?projectId`、`POST /entries`、`PATCH /entries/:id`、`DELETE /entries/:id`、`GET /projects`、`GET /clients`、`GET /tags`、`GET /settings`、`GET /config`（`aiProvider` のみ使用）、`GET /reports?range&anchor&groupBy&clientIds&projectIds&tagIds`、`GET /reports/entries?...`、`POST /ai/generate-stream`（NDJSON）、`GET /events`（SSE）。形は `src/shared/types.ts` を正とする。エラー本文のキーは `error`。

## 進め方

1. 骨組み: ウインドウ、ヘッダー、画面切替、メニューとショートカット、API クライアント、SSE。**最初にビルドが通るか（Xcode なしで動くか）を確認する**
2. カレンダー表示 → カレンダー操作
3. レポート表示 → 絞り込み・明細 → カスタム出力・AI 週報

各段階で今の React 版（`npm run dev`）と並べて見比べる。
